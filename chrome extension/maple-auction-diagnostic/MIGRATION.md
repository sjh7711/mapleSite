# v0.5에서 v0.8로 마이그레이션

## v0.8.6 방어구 결과 URL 호환

- 경매장 폼의 `방어구 + 방어구` 선택이 결과 URL에서 `itemCategory=ARMOR_ARMOR`로 변환되는 동작을 반영합니다.
- 장신구의 `ARMOR_ACCESSORY`와 방어구의 `ARMOR_ARMOR`를 서로 교차 허용하지 않고 각각의 선택에만 대응시킵니다.
- 두 분류 모두 필터 검색 직후 20개 결과를 검증한 다음 `60개씩 보기`로 전환합니다.

## v0.8.5 장신구 결과 URL 호환

- 경매장 폼의 `방어구 + 장신구` 선택이 결과 URL에서 `itemCategory=ARMOR_ACCESSORY`로 변환되는 동작을 반영합니다.
- 필터 검색 직후 20개 결과 URL을 먼저 검증한 뒤 기존 방식대로 `60개씩 보기`를 선택합니다.
- 방어구 검색에는 장신구 전용 별칭을 허용하지 않으며 기존 수집 진행도와 query ID는 유지합니다.

## v0.8.4 장신구·방어구 고잠재 구간 검색

- 장비명을 지정하지 않고 장신구와 방어구를 분리해 STR·DEX·INT·LUK 고잠재 거래를 수집합니다.
- 장신구는 각 스탯을 `27~29%`, `30~32%`, `33% 이상`으로, 방어구는 `27~29%`, `30~32%`, `33~35%`, `36% 이상`으로 나눕니다. 올스탯은 두 분류 모두 `21% 이상`을 별도로 수집합니다.
- 경매장 화면에는 구간 최소값을 입력하고, 저장 직전에 구조화된 잠재 줄의 선택 스탯+올스탯 합계로 상한을 다시 검사합니다. 따라서 같은 스탯의 인접 구간에는 같은 거래가 중복 저장되지 않습니다. 올스탯 21% 이상 검색은 가격 비교용 별도 채널로 함께 남깁니다.
- 검색 폼에서 상위 `방어구`와 하위 분류 `장신구` 또는 `방어구`를 직접 선택하고, 제출 직전·결과 화면·구조화 툴팁의 분류를 각각 확인합니다.
- 신규 전역 검색은 30개이며 전체 물리 검색은 185개, 전역 검색은 35개입니다. 카탈로그 버전은 `2026-09-04.1`입니다.
- 기존 155개 검색의 조건과 안정 ID는 유지하므로 완료 기록을 다시 초기화하지 않습니다. 업데이트 뒤에는 새로 추가한 30개 검색만 미완료 작업으로 들어옵니다.
- 일반 검색 98회의 우선 목표는 baseline 33회, starforce 28회, main 28회, allstat 2회, accessory 2회, mitra 5회입니다. 남는 한도는 기존처럼 미완료 레인에 재배분됩니다.

## v0.8.3 조 단위 가격 지원

- 화면의 `1조`, `1조 1000억`, `2조 3456억 7890만 1234` 형식을 정확한 메소 정수로 변환합니다.
- 구조화 응답 가격과 화면 가격을 1조 이상에서도 손실 없이 대조하며, 기존 원본 재정규화에도 같은 변환을 적용합니다.

## v0.8.2 드롭·메획 필터 선택 수정

- 경매장 드롭다운의 실제 항목명인 **아이템 획득 확률 증가**, **메소 획득량 증가**를 정확히 클릭한 뒤 수치를 입력합니다.
- 검색 폼은 한 번만 준비하고, 클릭 단계에서는 준비된 값이 그대로인지 다시 검증합니다. 검색 간격 대기는 폼을 준비하기 전에 끝내 입력 후 즉시 제출합니다.
- 초기화 뒤 에디셔널·추가옵션·주문서 등 지원하지 않는 잔존 조건은 계속 차단하되, 이번 검색이 덮어쓸 잠재·가격·스타포스 입력은 최종 폼 검증으로 판정합니다.

## v0.8.1 실패 보류 작업 선택 재시도

- 수집 실행 카드에 **실패한 작업 모두 포함** 선택을 추가했습니다. 선택하면 다음 KST 날짜까지 보류된 실패 물리 검색을 현재 실행 대상에 다시 포함합니다.
- 실패 보류와 0건 결과 재확인 대기를 상태에서 명시적으로 구분합니다. 선택 재시도는 실패 사유에만 적용되며, 빈 결과의 1·3·7·14일 backoff는 그대로 유지합니다.
- 강제 포함 대상은 수집 시작 시점의 고유 물리 검색 ID로 고정하고, 요청 예약에 성공한 검색은 현재 실행의 강제 대상에서 제거합니다. 같은 보류 작업이 한도를 반복 소모하지 않습니다.
- 기존 상태에 보류 사유가 없으면 `consecutive_empty_results`, `failures`, retry 표식을 순서대로 살펴 빈 결과와 실패를 추론합니다.

## v0.8.0 전역 드롭·메획 검색과 마이스터 3종

- 고정 카탈로그는 151종(P1 141종, P2 10종), 실제 물리 검색은 155개입니다.
- 마이스터링·마이스터 이어링·마이스터 숄더는 접두어로 합치지 않고 각각 자동완성에서 정확한 장비명을 선택합니다. 각 장비의 기본·0성·17성 이상 검색을 독립적으로 검증하고 저장합니다.
- 전역 검색은 고성 23성·24성·25성 이상 3개와 메소 획득량 증가 20% 이상·아이템 획득 확률 증가 20% 이상 2개를 합쳐 5개입니다.
- 드롭·메획 전역 검색은 카탈로그 밖 장신구도 저장하며, 두 검색의 잠재 줄을 메획 40%, 드롭 40%, 메획 20%+드롭 20%, 메획 20%, 드롭 20%의 5개 목표로 로컬 후분류합니다. 다섯 목표마다 검색을 반복하지 않습니다.
- 일반 검색 98회의 우선 목표는 baseline 48회, starforce 43회, accessory 2회, mitra 5회입니다. 레인별 수치는 하드 상한이 아니며 기존 재배분·복구 규칙을 유지합니다.
- 기존 원본과 완료된 호환 검색은 유지합니다. 새 전역 검색과 정확 검색으로 바뀐 마이스터 작업만 새로운 쿼리로 수집합니다.

## v0.7.9 광역·장비군 검색 안정화

- 전체 장비와 에테르넬·아케인셰이드·앱솔랩스·카루타 장비군 검색은 결과 행의 이름이 검색어와 완전히 같지 않아도 새 검색 결과와 DOM 안정화를 승인합니다.
- 정확 장비명 검색은 이전처럼 모든 결과 행의 이름 일치를 강제합니다.
- 고정 조사 목록 밖의 장비는 저장 단계에서 계속 제외하며, 정확 검색의 안전성 검증은 완화하지 않습니다.

## v0.7.8 장갑 오토스틸 잠재 보존

- `공격 시 n% 확률로 오토스틸` 잠재를 `AUTO_STEAL` 코드와 `%` 단위로 구조화해 `UNKNOWN`으로 빠지지 않게 합니다.
- 구조화 툴팁 API, 과거 DOM 원문, 기존 `capture.v2` 재정규화 경로에 동일한 파싱 규칙을 적용합니다.
- `normalizer 0.7.2`는 기존 원본을 변경하지 않고 장갑 오토스틸 옵션을 재해석합니다.

## v0.7.7 기본 시세 최소가격

- 표준 `BASE_ANY` 검색 52개에 최소 가격 5,000만 메소를 입력합니다. 이는 스타포스 0성 이상·잠재 필터 없음 기본 표본이 저가 매물 500건으로 먼저 잘리는 현상을 줄이기 위한 하한입니다.
- 정확히 0성, 17성 이상, 서버 잠재 필터, 전체 장비 23·24·25성 이상 검색과 특수 단일 검색에는 이 가격 하한을 적용하지 않습니다.
- 가격은 화면의 `최소 가격` 입력칸에 직접 넣고 제출 직전과 결과 페이지마다 다시 검증합니다. 쉼표가 표시된 값도 같은 메소 정수로 판독합니다.
- 검색 의미가 바뀐 기존 기본 시세 완료 기록만 새 작업으로 다시 수집하며, 나머지 스타포스·잠재·전역 검색 진행도는 유지합니다.

## v0.7.6 0성 전 페이지 수집과 검색 간격

- 0성 보강 검색도 첫 페이지에서 다음 결과가 확인되면 페이지네이션의 정확한 `2`, `3` 숫자 버튼을 차례로 눌러 실제 결과 끝 또는 500건까지 저장합니다. 검색 횟수는 최초 필터 검색 1회만 사용합니다.
- 연속된 필터 검색 클릭 사이에 최소 10초 간격을 둡니다. 결과가 0건이거나 처리 중 오류가 발생해도 마지막 클릭 시각을 수집 상태에 보존합니다.
- 숫자 페이지 이동과 같은 결과 페이지의 응답 복구 새로고침은 새 필터 검색이 아니므로 10초 제한에 포함하지 않습니다.
- 기존에 첫 페이지만 저장한 0성 작업은 다른 완료 작업을 초기화하지 않고 자동으로 미완료 처리되어 새 sweep으로 다시 수집됩니다.

## v0.7.5 숫자 직접 이동 안전성

- 후속 페이지와 중단 재개는 결과 화면의 정확한 숫자 버튼만 한 번씩 누릅니다. 화살표, URL의 `page` 변경, 비공개 API 재요청은 수집 경로에서 제거했습니다.
- 중단된 `pN`은 직전 저장 페이지 숫자를 눌러 구조화 응답 서명을 확인한 뒤 `N` 숫자를 누릅니다. 현재 검색과 과거 체크포인트가 다르면 서로 합치지 않고 현재 1페이지부터 새 sweep으로 다시 저장합니다.
- 숫자 버튼을 누르기 전후에 경매장 상단 `검색 횟수 n / 100`을 반드시 읽고 사용량과 한도 모두 같은지 확인합니다. 표시를 읽을 수 없거나 값이 변하면 저장하지 않습니다.
- 새 결과의 페이지 수가 줄어 재개할 숫자가 사라졌다면 이전 결과와 섞지 않고 현재 1페이지부터 새 sweep으로 수집합니다.
- 재시도 작업이 다시 중단돼도 페이지 번호·누적 상태·직전 페이지 서명을 다음 실행까지 보존합니다.
- 페이지 훅 통신을 v2로 분리해 이미 열린 탭에 남은 구형 직접 복구 경로를 사용하지 않습니다.

## v0.7.4 숫자 페이지 버튼 순회

- 후속 페이지는 URL이나 비공개 API를 직접 호출하지 않고, 결과 화면 페이지네이션의 정확한 목표 숫자 버튼을 한 번 눌러 이동합니다. 현재·목표 숫자 버튼을 하나로 확인할 수 없으면 우회하지 않고 복구 대상으로 남깁니다.
- 모든 페이지에서 검색 키·필터·정렬·60개 보기·검색 횟수와 화면 매물의 순서·이름·가격을 구조화 응답과 대조합니다.
- 중간 페이지 실패·관리자 중단 시 저장된 페이지 번호와 누적 페이지 상태를 유지합니다. 새 필터 검색으로 1페이지를 확인한 뒤 해당 페이지 숫자를 직접 눌러 이어서 수집합니다.
- 확장 업데이트 뒤 `chrome://extensions`에서 확장을 새로고침하고 기존 관리자 창과 경매장 탭을 다시 열어야 합니다.

## v0.7.3 실제 툴팁 API 호스트 지원

- 판매완료 툴팁의 실제 요청 호스트인 `api.mskr.nexon.com`을 권한·페이지 응답 훅·브라우저 네트워크 진단의 허용 목록에 추가했습니다.
- 구조화 캡처는 허용된 두 호스트의 정확한 `/v1/market/web/items/searches/sold/{UUID}/tool-tip` 경로만 받으며, 그 밖의 출처는 계속 거부합니다.
- API 요청도 진단 내보내기에서 전체 URL·검색 키·계정·캐릭터 ID·헤더 없이 축약해 기록합니다.

## v0.7.2 네트워크 진단과 수집 진행도 초기화

- 관리자에 **전체 네트워크 진단**을 추가했습니다. 연결된 경매장 탭의 완료·오류·리다이렉트 요청을 Chrome `webRequest`에서 관측해, DevTools에는 `/tool-tip`이 보이지만 페이지 훅에는 없는 상황을 구분합니다.
- 네트워크 진단은 응답 본문·전체 URL·헤더·계정 ID·캐릭터 ID·검색 키를 기록하지 않습니다. 알려지지 않은 경로는 허용된 템플릿으로 축약하며 결과가 0건이어도 복사할 수 있습니다.
- **수집 진행도 초기화**는 중단된 수신 원본을 먼저 복구하고 작업 완료·재시도·재확인 상태와 당일 순회 배분만 초기화합니다. 기존 `raw/`, IndexedDB 미저장 페이지, 누적 원본, 필터 검증, 오늘 검색 횟수와 한도 세션은 유지합니다.
- 서비스 워커와 새 `webRequest` 권한이 추가되므로 업데이트 뒤 `chrome://extensions`에서 확장을 새로고침하고, 기존 관리자와 경매장 탭을 다시 열어야 합니다.

## v0.7.1 구조화 응답 복구

- 사이트가 `fetch` 또는 XHR 함수를 다시 설치해도 현재 훅 상태를 확인하고 자동으로 다시 연결합니다.
- DevTools에는 `/tool-tip` 요청이 보이지만 기존 가로채기 캐시에 없는 경우, 현재 검색과 일치하는 동일 출처 Resource Timing을 이용해 그 응답을 한 번 다시 읽습니다. 검색 횟수와 hover는 사용하지 않습니다.
- 구조화 응답 대기 시간을 늘리고, 현재 검색 키·페이지 크기·정렬이 다른 응답인지 구분해 안내합니다.

## v0.7.0 구조화 응답 수집

- 목록 행에 마우스를 올려 DOM 툴팁을 읽던 자동 수집 경로를 폐기했습니다. 판매완료 검색이 반환하는 `/tool-tip` JSON 응답에서 스타포스·주문서·추옵·윗잠·에디를 직접 구조화합니다.
- `normalizer 0.7.0`은 캡처 전송 방식이 `tooltip_api`이고 해당 잠재의 출처가 `api_tooltip`일 때만 API의 `code`·`value`·`unit`·`params`를 보존합니다. 구형 DOM 캡처와 `raw.v1`의 과거 파서 값은 신뢰하지 않고 보존된 `raw`를 현재 규칙으로 다시 해석합니다.

## normalizer v0.7.1 API 스탯 출처 보존

- 구조화 툴팁 응답의 `source_hint`를 색상 DOM보다 우선해 `base`·`starforce`·`scroll`·`flame`·`other`를 분리합니다.
- 기존 `capture.v2` 원본은 바꾸지 않고 다시 정규화하면 주문서와 추가옵션 수치가 각 출처에 복구됩니다.
- 재정규화 시 `COOLDOWN_REDUCTION`, `STAT_PER_CHARACTER_LEVEL`, `HP_RECOVERY_ON_ATTACK`, `SKILL_AVAILABLE`을 구조화하므로 쿨타임 감소·9레벨당 스탯·공격 시 HP 회복·사용 가능 스킬이 `UNKNOWN`으로 남지 않습니다.
- 첫 필터 검색만 일일 검색 횟수를 사용합니다. 같은 검색의 후속 페이지는 최초 응답의 비공개 요청 정보를 메모리에서만 재사용해 화면 이동 없이 가져옵니다.
- 응답 캡처가 누락되면 검색 키를 유지한 채 현재 결과 페이지를 새로고침한 뒤 다시 확인합니다. 그래도 응답이 없으면 DOM hover로 우회하지 않고 안전하게 실패 처리합니다.
- `0성`, `9레벨당 STR/DEX/INT/LUK`, 모자 재사용 대기시간 감소를 API 원문과 수치로 보존하며, 기본/스타포스/주문서/추옵 스탯도 각각 분리합니다.
- 계정 ID·캐릭터 ID·검색 키·원본 요청 URL은 확장 메시지와 저장 파일에서 제거합니다. 원본 매물·아이템 식별자는 SHA-256 값만 저장합니다.
- 원본 스키마 이름은 `maple-auction.capture.v2`로 유지됩니다. 스타포스 근거에 `source: "api_response"`만 추가됐으며 기존 원본과 체크포인트는 그대로 사용할 수 있습니다.

## v0.6.16 레인 한도 재배분과 진행 상태 구분

- 일반 98회의 레인별 계획은 하드 상한이 아니라 우선 목표입니다. 먼저 계획이 남은 레인의 작업을 선택하고, 해당 레인에 실행 가능한 작업이 부족하면 남은 일반 한도를 완료되지 않았고 빈 결과 재확인 대기 중도 아닌 다른 레인의 검색에 재배분합니다.

- 예비 한도를 99·100번째 일반 검색으로 전환하는 조건은 바뀌지 않았습니다. 복구 검색을 한 번도 쓰지 않았고 대기 중인 복구도 없어야 합니다.
- 기존 `collector_state`와 레인 사용량은 초기화하지 않습니다. 업데이트 후 남은 작업부터 새 우선 목표·재배분 규칙으로 이어서 수집합니다.

| v0.5 | v0.6 |
|---|---|

서버 URL 코드가 검증되지 않은 HP·쿨감·크뎀·미트라 보조 판정은 기본 검색 페이지를 재사용합니다. 드롭·메획은 전용 전역 검색 2개의 결과를 5개 목표로 로컬 후분류합니다. 동일한 물리 `query_id`가 완료되면 형제 레인도 함께 완료하므로 같은 검색을 옵션별로 반복하지 않습니다.

현재 고정 카탈로그 구성은 마이스터 3, 에테르넬 35, 아케인셰이드 30, 앱솔랩스 30, 카루타 15, 칠흑 17, 광휘 6, 여명 4, 보스 장신구 11입니다. 이름·부위·기본 레벨은 [`tools/catalog.mjs`](tools/catalog.mjs)의 카탈로그 버전과 함께 검증됩니다.

## 업데이트 절차

1. 기존 `market-data` 폴더와 확장 폴더를 그대로 보관합니다. 기존 `raw/` 파일을 새 형식으로 직접 고치거나 이름을 바꿀 필요가 없습니다.
2. Chrome의 `chrome://extensions`에서 확장 카드의 **새로고침**을 누릅니다.
3. 열려 있던 메이플 경매장 탭도 새로고침합니다.
4. 확장 아이콘에서 새 **시세 수집 관리자**를 엽니다.
5. 기존 또는 새 `market-data` 루트 폴더를 선택하고 읽기·쓰기 권한을 확인합니다.
6. 고정 카탈로그가 151종, P1 141종, P2 10종, 물리 검색 185개로 표시되는지 확인한 뒤 수집을 시작합니다.

폴더 핸들은 브라우저가 다시 권한 확인을 요구할 수 있습니다. 같은 폴더를 다시 선택해도 기존 파일을 덮어쓰지 않습니다.

### 업데이트 당일의 100회 한도

v0.5에는 v0.6 형식의 일일 검색 장부가 없으므로, 업데이트 전에 그날 이미 수행한 사이트 검색 횟수를 로컬 상태만으로는 복원할 수 없습니다. 경매장 화면이 `사용량 / 100`을 제공하면 v0.6은 그 수치보다 로컬 카운터를 낮추지 않도록 동기화합니다. 그래도 KST 당일 검색을 이미 많이 했다면 사이트의 표시 사용량을 먼저 확인하고, 충분한 잔여 한도가 있는 날 또는 다음 KST 날짜에 자동 수집을 시작하세요.

v0.6에서 기록을 시작한 뒤에는 요청 전 예약, `reserved -> requested -> received -> committed` 단계와 일반 98회·복구 예비 2회를 보수적으로 계산합니다. 날짜가 바뀌어도 카탈로그 진행 지점과 미저장 페이지는 유지되고 일일 카운터만 초기화됩니다.

## 사용자 프리셋 처리

v0.5의 `chrome.storage.local` 키 `mapleAuctionSearchPresetsV1`은 v0.6 고정 카탈로그로 변환하지 않습니다. 두 체계는 대상과 우선순위가 다르기 때문입니다.

- v0.6 자동 스케줄러는 이 키를 조사 목록으로 사용하지 않습니다.
- 업데이트가 기존 프리셋을 151종 카탈로그에 합치지 않습니다.
- 고정 카탈로그를 바꾸려면 코드의 카탈로그 버전·수량 검증과 함께 변경해야 하며 관리자 화면에서 임의 항목을 추가하는 방식이 아닙니다.

## 브라우저 상태 마이그레이션

v0.6의 복구 저장소는 IndexedDB `maple-auction-jsonl` 버전 2입니다.

```text
settings
collector_state["primary"]
page_captures[page_capture_id]
```

- `settings`에는 폴더 핸들과 같은 설정을 둡니다.
- `collector_state`에는 KST 한도, 레인 사용량, 검색 시도, 페이지 크기 보정, 재개 지점을 둡니다.
- `page_captures`에는 응답을 받았지만 아직 파일 커밋 확인이 끝나지 않은 페이지를 둡니다.
- `chrome.storage.local["mapleAuctionCollectorCheckpointV1"]`은 작은 미러일 뿐이며 IndexedDB 페이지 대기열을 대신하지 않습니다.

페이지 파일 쓰기는 멱등적입니다. 같은 대상 파일에 같은 내용이 이미 있으면 커밋된 것으로 확정하고, 내용이 다르면 기존 파일을 덮지 않고 `_recovered_...` 파일을 새로 만듭니다.

업데이트나 창 종료 중 끊긴 시도의 복구 원칙은 다음과 같습니다.

| 마지막 단계 | 재개 동작 | 새 검색 예약 |
|---|---|---|
| `reserved` | 사용하지 않은 예약을 반환하고 작업을 다시 스케줄 | 필요하되 반환된 한도를 다시 쓰므로 사용량 증가 없음 |
| `requested` | 응답 확인이 없으므로 같은 페이지 재요청 | 필요 |
| `received` | IndexedDB의 페이지를 폴더에 커밋 | 불필요 |
| `committed` | 완료된 페이지로 건너뜀 | 불필요 |

관리자의 **진행 상태 내보내기**는 `manifests/maple-auction_collector-state_<timestamp>_<ID8>.json`을 만듭니다. 이 파일은 진단과 인계용이며 `raw/` 페이지를 대신하지 않습니다.

## 기존 원본 호환성

`tools/normalize.mjs`는 다음 입력을 읽습니다.

- `maple-auction.raw.v1` 매물 JSONL
- v0.5의 단일 `maple-auction.capture.v2` 배치 JSON
- v0.6의 `capture.v2` 페이지 봉투 JSONL

```powershell
node tools/normalize.mjs "경로\raw\기존-또는-v0.6-원본"
```

입력 원본은 읽기 전후 바이트가 같은지 확인하며, 결과는 별도의 `normalized/` 파일에 씁니다. 기본 출력은 새 파일 전용 생성이므로 같은 이름을 조용히 덮어쓰지 않습니다.

기존 원본에 없던 사실을 마이그레이션 과정에서 추측하지 않습니다.

- 네이티브 근거가 없는 과거 파생 `listing_id`는 정규화 시 `listing_id: null`로 두고 비교용 `listing_fingerprint`로 분리합니다.
- 근거 없이 파싱되지 않은 스타포스를 임의 값으로 바꾸지 않습니다. 다만 화면 제출이 검증된 정확 범위 검색(`0~0성`, `23~23성`, `24~24성`)은 해당 필터를 명시적인 추론 근거로 사용합니다. `25성 이상`은 열린 범위라 정확값을 추론하지 않습니다.
- 카탈로그 조인 근거가 없는 과거 장비의 `base_level`은 `null`로 유지합니다.
- 복구할 수 없는 가위 횟수나 화면 메타데이터도 `null`로 유지하고 품질 경고를 남깁니다.

## 학습 데이터 재생성

v0.6의 네이티브-ID 규칙을 적용하려면 기존 정규화 결과를 그대로 이어 붙이기보다 보관된 원본에서 다시 정규화하고 학습 CSV를 생성하는 편이 안전합니다.

```powershell
node tools/normalize.mjs "경로\raw\원본.jsonl"
node tools/build-training.mjs "경로\normalized\정규화.jsonl" "경로\training\auction-sold.csv"
```

학습 생성기는 다음 규칙을 적용합니다.

- 판매완료(`sold`)가 아닌 행은 출력하지 않습니다.
- `listing_id_source === "native"`인 동일 `listing_id`는 병합합니다.
- 네이티브 ID가 없으면 서로 다른 수집 시도에서 장비·지문·거래일·가격·월드가 모두 같은 fallback 관측만 중복으로 병합합니다.
- 한 시도 안의 동일 행 개수 중 최댓값은 보존해 실제로 여러 개 거래된 같은 가격·옵션 매물을 한 행으로 줄이지 않습니다. 지문 하나만으로는 합치지 않습니다.
- 병합 시 `matched_preset_ids_json`과 `selection_channels_json`만 합칩니다.

여러 정규화 파일을 하나의 CSV로 합치는 경우에도 같은 규칙을 전체 입력에 적용해야 합니다. 파일별로 기본 `auction-sold.csv`를 반복 생성하면 마지막 실행이 같은 출력 경로를 갱신하므로, 보관이 필요하면 명령의 두 번째 인수로 서로 다른 출력 파일을 지정하세요.

## 자립형 마이그레이션 fixture

자동 테스트는 저장소 안의 합성 표본만 사용합니다.

```text
tests/fixtures/sample-raw-v1.jsonl
레코드 수: 3
SHA-256: f37a53ba604e587b36414960452f2fece81379fdd6026d4effc13e79b8804a38
```

이 fixture에는 사용자 계정·판매자·제작자·쿠키·토큰 같은 개인 필드가 없으며, 저장소 상위 경로의 `.bak` 파일이나 실제 사용자 캡처에 의존하지 않습니다. SHA-256은 fixture가 바뀌었는지 확인하기 위한 값이지 매물 중복 제거 ID가 아닙니다.

Node.js 20 이상에서 다음을 실행합니다.

```powershell
npm test
```

## 마이그레이션 확인 목록

- 관리자에 카탈로그 `151 / P1 141 / P2 10`, 물리 검색 185개가 표시되는가
- 마이스터링·마이스터 이어링·마이스터 숄더가 각각 정확 장비명 검색으로 실행되는가
- 전역 검색 35개(고성 3개, 드롭·메획 2개, 분류별 고잠재 30개)와 드롭·메획 5개 로컬 목표가 구분되는가
- 장신구·방어구의 스탯 구간이 겹치지 않고, 올스탯이 개별 STR·DEX·INT·LUK 구간에 합산되지 않는가
- 자동 검색 주소가 `/price`, 정확명 또는 허용 접두어 부분검색, 최근 거래순인가
- 일반·예비·전체 한도가 `98 / 2 / 100`으로 표시되는가
- 필터 검색 결과가 생성된 뒤 60개씩 보기를 확인·선택하고 최종 결과도 `limit=60`인지 검증하는가
- 페이지마다 `raw/*.jsonl` 파일이 생기며 기존 파일을 덮지 않는가
- 전 페이지 대상이 같은 검색 키로 최대 500건까지 순회하고, 일시정지 후 미완료 또는 실패한 페이지부터 재개하는가
- 미저장 페이지 확인과 상태 내보내기가 서로 다른 동작인가
- 학습 CSV가 sold만 포함하고 네이티브 ID 없는 행을 삭제하거나 합치지 않는가
- 원본·정규화·학습 결과에 판매자·제작자·인증정보·전체 HTML이 없는가
