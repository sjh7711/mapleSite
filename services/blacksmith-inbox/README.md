# Inbox VM APIs

The production frontend calls `https://maple.hoegifarm.duckdns.org/starforce-api/api/blacksmith-inboxes` directly; preview uses `/starforce-preview-api/api/blacksmith-inboxes`. Each environment has a separate SQLite database, process, exact allowed frontend origin, and pair of private bridge/proxy keys. SQLite uses WAL, FULL synchronous durability and a dedicated worker thread, sharing the validated Pages API and SQL migrations.

## Build and run

Use Node 22.23.4. Run `node services/blacksmith-inbox/build.mjs`, then set `INBOX_API_CONFIG` to a private JSON file and run `node services/blacksmith-inbox/service.mjs`. The installed systemd units are `starforce-inbox-production.service` (loopback 4281) and `starforce-inbox-preview.service` (4280). Nginx provides HTTPS through isolated locations; other VM applications keep their routes.

Configuration fields: `port`, `database`, `frontendOrigin` (exact production or preview origin), `sitekey`, `verifyUrl` (the same frontend's `/api/internal/blacksmith-verify`), and independently generated 64-hex `proxyKey` / `bridgeToken`. Configs live in private `~/.config/starforce-inbox-{production,preview}/config.json`; databases and geo caches are under `~/.local/share/starforce-inbox-{production,preview}/`. Store configs with mode 0600. Nginx overwrites the proxy key and verified remote IP header. Never trust visitor-supplied forwarding headers. Only the authenticated Pages bridge may supply the original visitor IP for legacy requests.

Pages retains administrator login/session checks and the existing Turnstile secret. Only creation, name lookup, submission and edits use its authenticated Siteverify endpoint. Owner/applicant polling and inbox reads/writes go directly to the VM. Administrator API and older frontend requests use the authenticated Pages-to-VM bridge. There is no automatic fallback to a second writable database.

SQLite keeps existing hashed browser capabilities, hashed IP identifiers, admission quotas, nickname reservations and expiry triggers. The VM rate limiter rejects reads and failures before DB access (60 reads/20 writes per client and 300 reads/120 writes per IP per minute). These short windows reset after service restart; persisted 3-per-30-minute submission and creation limits do not. Each IP may have only one active inbox across normal/private browsers, including paused inboxes; ending or expiry releases that slot. The insert checks this atomically, while the original browser can still recover a lost creation response. Pre-existing duplicate inboxes remain manageable. IP changes can bypass IP identity, and devices sharing a public IP share the same creation slot. A five-minute cleanup removes expired inboxes and history. Closed history remains admin-only for three days.

`POST /api/blacksmith-inboxes/lookup` (`name` and single-use `inbox_lookup` Turnstile token) opens an applicant page by an exact, case-sensitive blacksmith name (trimmed and NFC-normalized). It returns only the room ID and name, ignores expired rooms, and requires server-side bot verification and uses the same request limits for successful and unsuccessful lookups. The pre-creation dialog switches between reservation creation and name lookup using two header tabs; it does not expose a room directory or partial-name search.

`GET /api/blacksmith-inboxes/managed` discovers the active inbox created from the verified visitor IP, including paused inboxes. Browsers without a saved owner capability connect directly to its queue. Every owner read/write accepts either the original owner capability or the matching creator IP hash; IP discovery never issues a persistent capability. Thus private tabs and other devices sharing that public IP can view, process, block applicants and end the inbox without approval, as the site owner explicitly selected. Moving to another IP removes IP-based access; the original saved owner capability continues to work from other IPs. Applicant-only endpoints and site administrator authentication remain separate. Legacy inboxes without a creator IP hash retain capability-only access. All discovery requests use the normal read limits and no-store responses.

Changes to the shared handler require rebuilding `services/blacksmith-inbox/.build/handlers.mjs` and restarting both VM systemd services in addition to deploying the matching preview/production Pages builds. No database migration is required for IP management: it uses the existing creator IP hash column.

Apple Private Relay IPv4/IPv6 ranges are fetched from Apple's official CSV every 24 hours and compiled into merged intervals. A failed refresh retains the last valid cache. Applicants from those ranges can view and withdraw but cannot submit or edit, including via the legacy Pages bridge. The policy uses Nginx's verified peer IP, ignoring caller-supplied forwarding headers. Per-inbox owner blocks also reject the blocked applicant capability or IP until the inbox ends; they do not affect other inboxes.

Foreign IPs are also rejected for applicant submission/editing. Monthly [DB-IP Country Lite](https://db-ip.com/db/download/ip-to-country-lite) CSV releases (CC BY 4.0) are checked daily, cached privately and compiled into Korean IPv4/IPv6 intervals. Classification is local, without sending visitor IPs to DB-IP. Unknown/non-Korean IPs are denied; viewing, withdrawal and owner management remain available. The applicant page provides the required attribution. Country geolocation is approximate; Korean VPN/proxy exits cannot be distinguished from other Korean IPs by this rule. A valid cache is retained on update failure; without any valid database the service does not start.

## Validation and operations

- `node --test test/inbox-vm.test.mjs` checks real SQLite transactions, persistence, CORS, private bridge authentication, bot verification and completion notices.
- `node services/blacksmith-inbox/benchmark.mjs` creates and deletes its own temporary DB with 100 inboxes, 10,000 requests and five equipment entries each. It sends 100 requests/second for 30 seconds in each read-only and 80/20 read/write phase. It never accepts a deployed URL or live DB path.
- `systemctl status starforce-inbox-preview` and the public `/starforce-preview-api/healthz` check service health. Application logs exclude request bodies, tokens, nicknames and IPs.
- `starforce-inbox-production-backup.timer` and `starforce-inbox-preview-backup.timer` run hourly using SQLite's online backup API and keep private local snapshots for 24 hours. This protects against accidental local data changes; snapshots on the same VM do not protect against loss of its disk. The service does not automatically switch to D1.
- Before migration, put the target environment into maintenance, export D1 privately, import to a new SQLite database, validate counts and foreign keys, then enable the matching VM origin and frontend base together. Production was migrated on 2026-11-03 with all three existing closed history records preserved. Its legacy D1 cleanup schedule is disabled; VM cleanup runs every five minutes. Keep the original export for rollback. Once the VM accepts new writes, switching back to the old D1 without migrating those writes would lose them.

Completion notices use the request's server `completed_at` timestamp and expire after five minutes, including across page refreshes. Repeating the same completed state does not reset the timestamp. Requests completed before this timestamp was introduced are left unknown.
